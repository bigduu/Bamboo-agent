# Durable direct-parent forced approval request

This is the #1419 production consumer slice of #1335. An interactive local Bamboo Child's existing HostApprovalProxy forwards its existing typed forced permission request and the canonical per-Run logical creation identity. The Server's existing ParentAgentApprovalReviewer loads the actual durable Child and complete parent chain. IDs, Child birth/depth, direct parent, Root and Project must match; missing generation/creation and foreign or recreated identities deny before delivery.

Before any reviewer model call, the reviewer publishes a RuntimeInstruction to the direct parent's existing SessionInbox through SessionMessenger with RespectSpecificWait. Its stable ID includes Child birth, parent birth and the server-issued permission generation. A digest of the full typed operation binds exact retries; a changed operation with the same generation conflicts. The envelope is limited to 8192 serialized bytes. Display text is bounded and private browser resources, commands and network resources are redacted; raw operation summaries/matchers/workspace/transport fields are not persisted in the Inbox. The off-loop reviewer separately receives bounded transient typed tool/resource/operation-summary information. Actual commands stay distinguishable there, including Bash delete commands, without appearing in the durable audit. Private browser information, URI-bearing resources/summaries, redacted/missing fields, syntax-changing display projections and over-budget inputs deny before the model instead of asking it to guess. PermissionRequest has no separate action_details field; this slice uses its existing resource and operation_summary. Matchers/workspace/transport fields never enter that transient projection. The ordinary worker-local no-human reviewer remains unchanged.

Delivery or activation error denies without a reviewer call. After successful admission and activation, the full durable lineage is re-observed before model review. The existing reviewer still returns only its existing one-shot boolean; the record is not a permission grant, approval receipt, task assignment or user instruction. A later #1335 source slice adds a typed `ParentRequest` projection to this canonical record and validates its exact scope before review; it does not turn the record into a grant. This observational identity check does not introduce a new distributed mutation fence or hold locks across the provider await.

The original #1419 request followed the existing parent wait policy and did not interrupt a specific Child/Bash wait. A delivery followed by an activation failure could leave a durable request; an exact retry used the same Inbox identity. The later #1438 live-outcome slice persists a terminal decision and interrupts the current specific wait as described in `live-parent-permission-outcomes.md`. Cold Child resume, generic questions, escalation and the complete #1335 decision protocol remain unfinished. No HTTP messaging endpoint, new index or journal is added, and these slices do not close #1335/#791.

Prepared validation uses the real FileSessionInbox and real production reviewer with a counting provider: failed publication makes zero review calls, successful exact retry has one durable record, changed operations and foreign/missing identities deny. The native fixture in native_tool_ceiling.rs runs actual compiled serve/current_exe Child Write under an always-ask rule: the reviewer model sees the durable parent request before returning DENY, Write never occurs, and a cold Store retains the admitted request. These tests are not claimed executed until the coordinated Cargo gates complete.
