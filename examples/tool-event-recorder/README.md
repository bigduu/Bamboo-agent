# ToolEvent recorder plugin example

This is a deliberately small, native Bamboo service that records authorized
`ToolEventV1` projections as NDJSON. Its normal dependency graph ends at
`bamboo-plugin-protocol`, `serde`, and `serde_json`: it does not import the
server, installer, service manager, router, or tool executor.

The checked-in [`plugin.json`](plugin.json) requests only `metadata`. The
host therefore omits `tool_name`, `path`, `diff`, and `content`; the
[`metadata-only.file-changed.json`](examples/metadata-only.file-changed.json)
fixture shows the complete delivered shape. The schema is generated by the
public `bamboo_plugin_protocol::tool_event_v1_schema()` API and checked in at
[`schema/tool-event-v1.schema.json`](schema/tool-event-v1.schema.json).

## Build and stage a local bundle

Build the standalone binary from the repository root:

```console
cargo build --release -p bamboo-tool-event-recorder-example
```

Copy it to the exact native bundle location selected by `${platform_bin}`:

| Host | Bundle path | Repository test coverage |
|---|---|---|
| macOS | `bin/macos/tool-event-recorder` | Native subprocess and absolute POSIX paths |
| Linux | `bin/linux/tool-event-recorder` | Native subprocess and absolute POSIX paths |
| Windows | `bin/windows/tool-event-recorder.exe` | Native subprocess and absolute drive paths |

For example, on Linux:

```console
mkdir -p ./bundle/bin/linux
cp target/release/tool-event-recorder ./bundle/bin/linux/tool-event-recorder
cp examples/tool-event-recorder/plugin.json ./bundle/plugin.json
```

Before installation, write the recorder's service config to Bamboo's stable
per-plugin config location:

```json
{
  "output_path": "/absolute/path/to/tool-events.ndjson",
  "startup_log_path": "/absolute/path/to/recorder-starts.log",
  "startup_delay_ms": 0
}
```

The config path is
`<BAMBOO_DATA_DIR>/plugin_service_config/tool-event-recorder/config.json`.
Bamboo passes that path in `BAMBOO_PLUGIN_SERVICE_CONFIG`; it deliberately
survives bundle upgrade and uninstall. Then install the local bundle against a
running server:

```console
bamboo plugin install ./bundle
bamboo plugin list --json
```

Grant changes are host policy, not manifest self-authorization. The example
requests metadata only. To try path delivery, update a copied manifest to
request `metadata` and `paths`, then send an upgrade request whose
`event_sink_grants` explicitly grants both ids. An omitted grant on a fresh
install means metadata only; an omitted grant during update preserves only
previous grants still requested. Newly requested observation is never granted
implicitly.

## Delivery contract

- Delivery is best-effort and at-most-once, never exactly-once. Queue admission
  is not an acknowledgement, there is no durable spool, and Bamboo does not
  retry, replay, or catch up events. A crash/restart can discard records that
  were not fully written.
- Events accepted by one live sink/process generation retain admission order.
  A restart or upgrade creates a new service generation; a permission update
  creates a new observation-policy generation. Ordering is not promised across
  those generation boundaries.
- Tool execution never waits for this process or its queues. A slow/crashed
  recorder increments bounded diagnostics and may lose events; it cannot
  change the tool result.
- This manifest uses a two-event sink queue and a 16,384-byte event limit. The
  manifest default is 64 queued events, the per-sink maximum is 1,024, and all
  sinks in one manifest may declare at most 64 MiB of aggregate buffering. The
  downstream service-input queue additionally caps one physical NDJSON line,
  including its newline, at 1 MiB.
- Public protocol limits also cap session/root/call ids, tool name, path,
  projected diff (4 KiB), projected content (8 KiB), and the complete JSON
  event (16 KiB). Bounds are UTF-8 wire bytes, and the final complete-event
  bound is checked after JSON escaping. Oversize events are dropped before
  service delivery.
- Metadata is the safe minimum. Even with explicit `paths` authorization,
  sensitive or lexically unsafe paths are omitted and replaced with a stable
  `sensitive_path` or `unsafe_path` reason; redacted events contain no
  diff/content payload.
- Protocol version `0` is invalid and installation is rejected. Version `1`
  uses the schema in this directory. A future non-zero version remains
  installable but inactive on a v1 host and receives no events until the host
  supports it.

## Diagnostics

`bamboo plugin list --json` exposes bounded, payload-free state: requested and
granted permissions, service/sink generation, observation-policy generation,
and `delivered`, `queue_full`, `service_down`, `serialization`, and `oversize`
counters. `delivered` means admission to the exact current service-generation
input queue, not that the recorder flushed or durably stored the line.
`waiting_for_service` means the process has no writable current generation; an
unsupported protocol reports an inactive reason. The recorder
prints malformed-config/input diagnostics to stderr without echoing service
configuration or event payloads.

The lifecycle test uses this package's independently built recorder binary on
macOS, Linux, and Windows. Cargo exposes it to the integration test through
`CARGO_BIN_EXE_tool-event-recorder`; the test stages that binary at the native
platform path above, then covers install, a real successful `Write`, redaction,
queue pressure, crash/restart, permission-changing upgrade, uninstall, and
boot reconcile. CI on each target is the authoritative record for that target;
one host run is not evidence for the other operating systems.
